# 代码阅读指南

这份指南按一次真实 Run 的执行顺序阅读，不按文件名排序。

## 1. 先看公共入口

从以下文件开始：

1. `deepresearch/cli.py`
2. `deepresearch/service.py`
3. `deepresearch/schemas.py`

`cli.py` 将命令行参数转换成 `ResearchRequest`。项目只有统一的 `research` 模式，CLI 不提供 `--mode`。

`service.py` 组装 LLM、Profile、Skill Registry、Checkpoint 和 `ResearchGraph`。Skill 由 `skill_loader.py` 从项目级 `skills/` 目录动态发现并绑定运行入口。

`schemas.py` 是运行协议。优先理解：

```text
ResearchRequest
ResearchConstraints
ResearchOptions
ResearchScope
RunBudget / TaskBudget
ResearchTask / TaskSufficiency
ResearchContribution
ResearchGap
SynthesisDecision
Source / Evidence / Claim / Link / Citation
```

`ResearchMode.DEEP_SEARCH` 和 `DEEP_REPORT` 只是指向同一个 `RESEARCH` 枚举成员的源码兼容别名，不对应不同逻辑。

## 2. 看四类 Prompt

打开 `deepresearch/prompts.py`：

### Planner

`PLANNER_SYSTEM_PROMPT` 负责：

- 判断 straightforward、depth-first 或 breadth-first；
- 识别答案要求、实体和时间边界；
- 第一轮规划必要研究方向；
- 后续轮次只处理 Synthesizer Gap；
- 为 Worker 生成完整任务合同；
- 选择来源策略和任务证据下限。

### Worker

`WORKER_SYSTEM_PROMPT` 有两个调用阶段：

```text
strategy
  输入：任务合同、历史 Claim、Synthesizer Gap、已尝试 Query
  输出：研究判断、新 Query、目标来源和风险

reflection
  输入：已验证 Claim、Source 元数据、失败和充分性指标
  输出：成果摘要、知识缺口和来源冲突
```

Worker 不写最终报告，也不能把 Search Snippet 或模型记忆当证据。

### Extractor

`EXTRACTOR_SYSTEM_PROMPT` 只处理一个网页 Chunk。它必须返回 Claim 和正文连续 Quote。网页正文由 `security.wrap_untrusted_content()` 包装。

### Synthesizer

`SYNTHESIZER_SYSTEM_PROMPT` 判断材料是否足以写报告；`REPORT_SYSTEM_PROMPT` 只在研究停止后，根据 Claim ID 生成结构化报告。

## 3. 看主图

打开 `deepresearch/graph.py`，按节点顺序读：

```text
_prepare_request
_normalize_scope
_plan_research
_dispatch_tasks
_worker_node
_synthesize_research
_route_synthesis
_build_output
_citation_gate
_finalize_run
_persist_artifacts
```

主循环：

```text
plan_research
  -> Send(research_worker...)
  -> synthesize_research
       -> need_more -> plan_research
       -> ready/partial -> build_structured_output
```

`round_no` 从 1 开始，最多为 `ResearchOptions.max_rounds`；`standard` 当前为 4 轮。

`_synthesize_research()` 还检查：

- 是否仍有 Search/Fetch/Token；
- 是否超过 Wall Time；
- 本轮是否产生新证据、来源或有效 Contribution；
- 是否已经到最大轮次。

因此循环不会无限运行。

## 4. 看 Planner 如何生成 Task

打开 `agents.py` 的 `Planner.plan()`。

Planner 输入包括：

```text
question / objective
current_date / date_boundary / locale
round_no / max_rounds
required_dimensions / suggested_dimensions
actionable_gaps_from_synthesizer
attempted_queries
validated_evidence_summary
remaining_round_budget
```

输出的 `ResearchTask` 包含：

```text
objective
research_dimension
task_type
key_questions
queries
preferred_source_types
verification_strategy
expected_output
sufficiency
budget
```

LLM 生成失败时 Planner 使用确定性 Fallback，Run 不会因为一次规划 JSON 失败直接崩溃。

## 5. 看 Research Worker

继续看 `ResearchWorker`：

1. `_strategy()` 调 Worker Prompt，去除历史重复 Query。
2. `_search_with_loop()` 为当前 Worker 创建私有 `AgentLoop`。
3. Agent Loop 调用角色授权的 Search Skill；每波最多执行六条查询，随后先抓取和评估证据，再决定是否开启下一轮搜索。
4. `run()` 对候选 URL 去重，并优先不同注册域和开放学术来源。
5. 在 Fetch 前执行 allowed/blocked domain。
6. `safe-fetch` Skill 执行 SSRF 和 Redirect 检查；评测版还会对访问失败的 DOI 解析开放全文、摘要或书目信息。
7. `_content_windows()` 切分长正文。
8. `_build_extraction_prompt()` 构造不可信正文抽取请求。
9. `filter_extracted_claims()` 校验 Quote 和数字。
10. `records_from_document()` 写 Source/Evidence/Claim/Link。
11. Fetch 额度来自本轮共享租约池；Worker 结束时会归还未用额度。
12. 达到 Task Sufficiency 时提前停止。
13. `_reflect()` 总结可用成果和下一轮缺口。

一次 Fetch 不等于一次成功抽取。只有真正生成通过校验的 Evidence 才增加 `successful_extractions`。

## 6. 看 Synthesizer

`Synthesizer.assess()` 同时使用两层判断。

确定性层检查：

- 当前 Worker 是否达到 Task Sufficiency；
- 是否存在有效 Claim；
- 显式 Required Dimension 是否有验证证据覆盖；
- Source Tier 是否允许发布。

LLM 层检查：

- Claim 是否真正回答问题；
- 时间边界是否满足；
- 是否存在未解决的核心冲突；
- 是否能组织成有意义的报告；
- 缺口是否重要且可以继续研究。

`ready` 不能覆盖失败的确定性硬门禁。`need_more` 必须返回结构化 `ResearchGap`：

```text
dimension
missing_information
why_needed
preferred_source_types
verification_requirement
priority
```

下一轮 Planner 直接消费这些字段。

## 7. 看报告和引用

`Synthesizer.write()` 构建 Claim Ledger，只允许报告 Prompt 选择已有 Claim ID。

然后 `evidence.validate_citations()` 检查：

```text
OutputParagraph
  -> CitationRecord
  -> ClaimEvidenceLink
  -> EvidenceRecord.quote
  -> SourceSnapshot.content
  -> SourceRecord
```

任何一环断裂、Quote 不存在或 Claim 数字不在 Quote 中，事实段落不能通过发布门禁。

## 8. 看 State Reducer

打开 `deepresearch/state.py`。

并行 Worker 会同时返回 Source、Evidence、Claim、Trace 和 Usage。Reducer 按稳定 ID 合并，而不是简单列表相加。

重要 Reducer：

- Task：`task_id`
- Plan/Planner/Synthesis Trace：`round_no`
- Worker Trace：`task_id + round_no + phase`
- Agent Loop Trace：`trace_id`（包含 Worker、迭代、Skill 调用和 observation）
- Source/Evidence/Claim/Link：各自稳定 ID
- Contribution：`task_id + attempt`
- Event：`event_id`，合并后按 sequence 排序

## 9. 看预算

打开 `deepresearch/budget.py`。

`remaining_task_budget()` 从全局预算扣除已用资源和 Planner/Synthesizer 预留，并按轮次限制研究池。

`split_task_budget()` 再将本轮预算分给 Planner 创建的 Worker。数量由 `ResearchOptions.max_workers` 限制，默认 6，上限 16。

不要把 Task Budget 理解成“必须花完”；Worker 达标后会提前停止。

## 10. 看审计产物

打开 `deepresearch/artifacts.py`。

调试多轮问题时按顺序看：

1. `research-plan.json`：每轮计划和 Task Contract。
2. `planner-traces.json`：Planner 原始 JSON。
3. `worker-traces.json`：Worker Strategy/Reflection。
4. `agent-loop-traces.json`：每个 Worker 的 Skill 调用、observation 和停止原因。
5. `search-traces.json`：Query 和候选 URL。
6. `fetch-traces.json`：抓取成功、失败或无 Evidence。
7. `extraction-traces.json`：抽取 JSON、拒绝原因和 Token。
8. `synthesis-traces.json`：为什么继续或停止。
9. `report-trace.json`：最终报告选择了哪些 Claim。
10. `citation-gate.json`：发布门禁。
11. `events.jsonl`：完整节点顺序。

## 11. 推荐断点

第一次调试建议设置：

```text
graph._normalize_scope
Planner.plan 调 LLM 前后
ResearchWorker._strategy
ResearchWorker.run 的 Search 和 Fetch 前后
filter_extracted_claims
records_from_document
Synthesizer.assess
graph._route_synthesis
Synthesizer.write
graph._citation_gate
```

## 12. 测试阅读顺序

```text
tests/fakes.py
tests/test_workflow.py
tests/test_extraction_pipeline.py
tests/test_security_and_evidence.py
tests/test_budget.py
tests/test_evaluation.py
```

重点测试：

- 第一轮失败后 `need_more -> Planner -> 第二轮 Worker`；
- 显式缺失维度如何逐轮补齐；
- 四类 Prompt 是否收到日期和任务合同；
- Worker 是否同时产生 Strategy 和 Reflection Trace；
- Tier 4、Canonical URL 和注册域门禁；
- Citation Gate 负例；
- SQLite Resume 不重复研究。

当前测试结果：`70 passed`。
